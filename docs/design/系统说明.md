# 校园集市 · 系统说明

> 项目：校园二手交易与物品流转平台（`campus-secondhand-platform`）
> 文档版本：v1.0　　编制日期：2026-11-08
> 对应需求：SRS-CSTP-001 v1.1
> 说明范围：系统定位、架构、功能、流程、数据、接口、安全、部署与验证；代码级实现细节见《系统实现说明》。

---

## 1. 系统定位

“校园集市”是面向校园内部用户的二手交易与物品流转平台。它把分散在群聊、朋友圈中的闲置交易，收敛为一条可搜索、可追踪、可审计的业务链路：

```
身份认证 → 发布审核 → 搜索发现 → 收藏咨询 → 待确认请求
        → 卖家接受 → 线下交付 → 双方确认 → 评价 / 举报 → 管理处置 → 统计分析
```

平台本身**不提供在线支付、资金托管和物流**，只负责信息匹配、状态约束、交付记录与违规治理。交易在校内线下完成，平台通过“双方确认”形成可追踪的成交记录。

> 教学模拟声明：本项目为课程项目实现，校园认证为模拟流程，演示账号、商品与交易数据均为虚构。

## 2. 建设目标与实现情况

| 目标 | 需求描述 | 本系统实现 |
|---|---|---|
| BG-01 提高匹配效率 | 关键词、类别、价格、成色、区域组合筛选 | 市场页支持五类条件 + 时间/价格排序，后端 SQL 动态拼接 |

| BG-04 提升治理能力 | 商品/用户/消息可举报，处置可审计 | 举报快照、管理员处理、账户处置、审计日志 |
| BG-05 支持运营改进 | 发布量、成交量、成交率、举报与处置统计 | 管理端统计仪表盘与趋势图 |

## 3. 用户角色

| 角色 | 定义 | 主要权限 |
|---|---|---|
| 游客 | 未登录用户 | 注册、登录、找回凭据、查看公开规则 |
| 未认证用户 | 已注册但未完成校园认证 | 维护个人资料、提交认证；**不能浏览商品与交易** |
| 已认证用户 | 认证通过且账户可用 | 浏览、收藏、咨询、发布、下单、评价、举报 |
| 买家 | 某笔订单中的购买方 | 创建待确认请求、确认交付、评价、取消（受状态限制） |
| 卖家 | 某件商品/订单的出售方 | 发布、编辑、下架、接受/拒绝请求、确认交付、评价 |
| 管理员 | 平台运营人员 | 商品审核、举报处理、争议裁决、账户处置、统计、审计 |

买家和卖家不是账户类型，同一用户可在不同交易中承担不同角色；管理员不参与普通交易。

## 4. 系统范围

### 4.1 范围内

1. 注册、登录、找回凭据、校园身份认证、账户状态管理；
2. 商品草稿、提交审核、批准/驳回、编辑、主动下架、违规下架；
3. 商品浏览、关键词搜索、组合筛选与排序；
4. 收藏、取消收藏、基于商品的咨询会话；
5. 待确认请求、卖家接受/拒绝、取消与交易确认；
6. 线下交付时间/区域/备注、双方分别确认、争议提交；
7. 交易评价、商品/用户/消息举报及结果查询；
8. 管理员审核、举报处理、警告/限权/封禁/解封；
9. 商品、订单、举报状态流转与审计；
10. 发布、交易、评价、举报与处置的聚合统计。

### 4.2 范围外

- 在线支付、资金托管、退款结算、发票；
- 校外快递、即时配送、平台自建物流；
- 商品真伪、质量与合法来源的线下鉴定；
- 学校纪律处分或司法裁决；
- 拍卖、以物易物、多件购物车、校外公开交易。

## 5. 总体架构

```
┌──────────────────────────────────────┐
│ 浏览器（学生 / 管理员）                │
│ Vue 3 SPA + Element Plus + Pinia      │
└──────────────────┬───────────────────┘
                   │ HTTP/JSON + JWT
┌──────────────────▼───────────────────┐         ┌────────────────────────┐
│ Spring Boot 3 后端（8080）             │  JDBC   │ MySQL 8（3306）         │
│ Controller → Service → MyBatis Mapper │────────▶│ campus_secondhand       │
│ Spring Security（JWT）/ 定时任务       │         │ 15 张业务表             │
└──────────────────┬───────────────────┘         └────────────────────────┘
                   │ 本地文件
          backend/uploads（图片）
```

- **前端**：单页应用，负责页面渲染、表单校验、路由守卫与接口调用；开发期通过 Vite 代理访问后端。
- **后端**：无状态 REST 服务，负责认证鉴权、业务规则、事务与状态机、审计与通知。
- **数据库**：MySQL 保存全部业务数据；生成的唯一索引提供并发兜底。
- **文件**：商品图片保存在本地 `backend/uploads`，通过 `/uploads/**` 静态映射访问。

### 5.1 部署形态

| 环境 | 形态 |
|---|---|
| 开发 | 前端 `vite dev`（5173）代理 `/api`、`/uploads` 到后端 8080；MySQL 本机 |
| 生产（建议） | Nginx 托管 `frontend/dist` 静态文件，反向代理 `/api` 与 `/uploads` 到后端 8080；后端 jar 以服务方式运行 |

## 8. 核心业务流程

### 8.1 认证与发布审核

1. 用户注册，账户状态为“未认证”；
2. 提交学号、姓名、学院，模拟认证通过后获得交易权限；
3. 卖家创建商品草稿，填写标题、分类、成色、描述、价格、交付区域与图片；
4. 提交审核，系统校验必填项与至少 1 张图片；
5. 管理员批准后商品上架；驳回必须填写原因；
6. 卖家修改被驳回商品后可重新提交；在售商品修改关键字段会重新进入待审核。

### 8.2 交易主流程

1. 买家通过关键词与组合筛选找到在售商品；
2. 查看详情、卖家信誉与风险提示，可收藏或发起咨询；
3. 创建待确认请求：不锁定商品，同一买家同一商品仅 1 条，单商品最多 10 条；
4. 卖家接受其中 1 条：系统原子地把请求转为“待线下交付”、商品转为“已锁定”，其余请求自动取消（未中选）并通知；
5. 卖家拒绝或买家取消时商品保持在售；
6. 超过 24 小时未处理的请求由定时任务自动取消。

### 8.3 交付与完成

1. 双方记录交付时间、区域与备注，变更写入留痕并通知对方；
2. 双方线下验货、付款、交付；
3. 买家确认交付，订单进入“买家已确认”；卖家确认则进入“卖家已确认”；
4. 双方均确认后，同一事务内订单完成、商品标记已售；
5. 一方确认后普通取消被拒绝，只能提交争议；
6. 完成后 7 天内双方可各评价一次。

### 8.4 举报与处置

1. 用户举报商品、用户或消息，系统保存对象快照与唯一举报号；
2. 管理员领取举报（待处理 → 处理中）；
3. 管理员判定成立/不成立/待补充；
4. 成立时自动执行处置：商品违规下架，或对用户警告/限权/封禁；
5. 处置人、时间、依据、理由与前后值写入审计日志；
6. 被处置方可申诉，管理员复核后维持或撤销；
7. 举报关闭，举报人收到可公开结果。

## 9. 状态模型

### 9.1 商品状态

| 状态 | 含义 | 主要转移 |
|---|---|---|
| `DRAFT` | 草稿 | 提交 → 待审核 |
| `PENDING` | 待审核 | 批准 → 在售；驳回 → 审核驳回 |
| `REJECTED` | 审核驳回 | 卖家修改 → 草稿；重新提交 → 待审核 |
| `ON_SALE` | 在售 | 接受请求 → 已锁定；卖家下架 → 已下架；管理员下架 → 违规下架 |
| `LOCKED` | 已锁定 | 取消/争议关闭 → 在售/已下架；双方确认 → 已售 |
| `SOLD` | 已售出 | 终态 |
| `OFF_SHELF` | 已下架 | 重新提交 → 待审核 |
| `VIOLATED` | 违规下架 | 修改后重新提交（管理员处置后） |

### 9.2 订单状态

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `PENDING_SELLER` | 待卖家确认（待确认请求） | 买家取消、卖家接受/拒绝、超时取消、未中选取消 |
| `DELIVERING` | 待线下交付 | 双方修改交付约定、确认交付、提交争议；无人确认时可取消 |
| `BUYER_CONFIRMED` | 买家已确认 | 卖家确认 → 完成；提交争议；买家重复确认幂等 |
| `SELLER_CONFIRMED` | 卖家已确认 | 买家确认 → 完成；提交争议；卖家重复确认幂等 |
| `COMPLETED` | 已完成 | 双方各评价一次（7 天内） |
| `CANCELLED` | 已取消 | 终态（记录取消类型与原因） |
| `DISPUTE` | 争议中 | 管理员裁决为完成或管理关闭 |
| `MANAGEMENT_CLOSED` | 管理关闭 | 终态 |

### 9.3 举报状态

| 状态 | 含义 |
|---|---|
| `SUBMITTED` | 待处理 |
| `PROCESSING` | 处理中（已领取） |
| `SUPPLEMENT` | 待补充证据 |
| `UPHELD` | 举报成立 |
| `REJECTED` | 举报不成立 |
| `PENDING_APPEAL` | 申诉中 |
| `CLOSED` | 已关闭 |

## 10. 数据模型

### 10.1 表分组

| 分组 | 表 | 说明 |
|---|---|---|
| 账户 | `sys_user`、`category` | 用户、认证、账户状态；商品分类 |
| 商品 | `item`、`item_image`、`favorite` | 商品主表、图片、收藏 |
| 沟通 | `conversation`、`message` | 基于商品的会话与消息 |
| 交易 | `trade_order`、`handover_record`、`handover_log`、`review` | 订单、交付记录、变更留痕、评价 |
| 治理 | `report`、`moderation_action`、`audit_log` | 举报、处置动作、审计日志 |
| 支撑 | `notification` | 站内通知 |

共 15 张表，字符集 `utf8mb4`。

### 10.2 关键约束

| 约束 | 实现 | 作用 |
|---|---|---|
| 同一商品最多 1 条活跃订单 | 生成列 `active_item_key` + 唯一索引 | 防止重复成交 |
| 同一买家同商品最多 1 条待确认请求 | 生成列 `pending_buyer_key` + 唯一索引 | 防止重复请求 |
| 同一用户同商品只有一条收藏 | `UNIQUE(user_id, item_id)` | 收藏幂等 |
| 同一订单每方只能评价一次 | `UNIQUE(order_id, author_id)` | 防重复评价 |
| 同一商品同一买家一个会话 | `UNIQUE(item_id, buyer_id)` | 会话复用 |
| 用户名、学号唯一 | `UNIQUE` | 账户唯一性 |
| 举报号、订单号唯一 | `UNIQUE` | 业务编号可追踪 |
| 审计日志只追加 | 不提供删除接口 | 证据链完整 |

### 10.3 数据访问原则

- 商品列表只返回“在售”商品；非在售商品仅本人/管理员可见。
- 订单、会话、举报详情仅参与者或管理员可读。
- 统计接口只返回聚合结果，不返回个人明细。
- 公开资料不返回学号、真实姓名、邮箱；联系方式按可见范围决定。

## 11. 接口设计

### 11.1 约定

- 基础路径：`/api`
- 认证：`Authorization: Bearer <JWT>`
- 响应：`{ "code": 0, "message": "ok", "data": ... }`
- 分页：`{ "records": [], "total": 0, "page": 1, "size": 10 }`
- 时间：ISO 本地时间字符串（如 `2026-11-08T10:30:00`）
- 金额：数字（元），`0` 表示免费流转

## 12. 权限与安全

| 场景 | 控制措施 |
|---|---|
| 未登录 | Spring Security 过滤器链返回 401 JSON |
| 未认证 | 浏览/发布/下单/评价/举报等接口服务端拒绝 |
| 限权/封禁 | 限制发布、下单、发送消息等写操作并返回明确提示 |
| 越权访问 | 服务端校验 owner/participant；商品、订单、会话、举报均不依赖前端隐藏按钮 |
| 密码 | BCrypt 加盐哈希；接口不返回密码字段 |
| 会话 | 无状态 JWT；每次请求从数据库加载最新账户与认证状态 |
| SQL 注入 | MyBatis 预编译参数；LIKE 通配符转义（`ESCAPE '!'`） |
| XSS | Vue 文本插值，不渲染用户 HTML；后端限制输入长度 |
| CSRF | 无 Cookie 会话，JWT 放在请求头，关闭 CSRF |
| CORS | 只允许配置的前端来源 |
| 文件上传 | 仅图片类型、≤5MB、UUID 文件名、路径规范化 |
| 隐私 | 公开资料脱敏；统计去标识；举报证据仅授权人员可见 |
| 审计 | 关键操作记录操作者、时间、对象、理由与前后值；不提供删除接口 |

## 13. 一致性与可靠性

1. **创建请求**：锁定商品行后校验“买家无重复请求、请求数 < 10”，再插入订单。
2. **接受请求**：固定“商品行 → 订单行”加锁顺序，在同一事务内完成请求状态、商品锁定与其他请求取消。
3. **唯一索引兜底**：即使应用层判断出现竞态，数据库也会拒绝第二条活跃订单或第二条待确认请求。
4. **双确认完成**：双方确认与商品售出在同一事务内更新；单方确认不会自动完成。
5. **乐观锁**：订单/商品/举报更新带版本号，避免并发覆盖。
6. **超时任务**：每 60 秒扫描超时待确认请求并逐条加锁取消。
7. **通知**：在业务事务提交后以独立事务落库；失败只记录 `FAILED`，不回滚业务。
8. **事务回滚**：接受、取消、确认、裁决等任一写入失败时整体回滚，保持状态一致。

## 14. 部署与运行

### 14.1 依赖环境

见《环境清单》。核心要求：JDK 21、Maven 3.9、Node 20+、MySQL 8.0。

### 14.2 启动步骤

```powershell
# 1. 初始化数据库
powershell -ExecutionPolicy Bypass -File .\scripts\init-db.ps1 -Password 你的密码

# 2. 启动后端（自动使用 JDK 21 与项目内 .m2repo）
.\scripts\start-backend.cmd

# 3. 启动前端
cd frontend
npm run dev      # 或安装 pnpm 后使用 pnpm dev
```

访问 <http://localhost:5173>。

### 14.3 演示账号

| 账号 | 密码 | 角色 |
|---|---|---|
| `admin` | `admin123` | 管理员 |
| `seller01` / `seller02` | `123456` | 已认证卖家 |
| `buyer01` / `buyer02` | `123456` | 已认证买家 |
| `newbie01` | `123456` | 未认证用户 |
| `banned01` | `123456` | 封禁用户 |

### 14.4 关键配置

- 数据库连接：`DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USERNAME`、`DB_PASSWORD`
- JWT：`APP_JWT_SECRET`（生产必须更换）
- 上传目录：`APP_UPLOAD_DIR`
- 跨域来源：`APP_FRONTEND_ORIGIN`
- 业务参数：超时小时数、单商品请求上限、评价窗口

### 14.5 生产部署建议

1. 使用 Nginx 托管 `frontend/dist`，反向代理 `/api` 与 `/uploads`；
2. 后端 jar 以 Windows 服务或 systemd 方式运行，配置健康检查；
3. MySQL 使用独立账号与强密码，定期备份；
4. 上传目录挂载独立磁盘或对象存储；
5. 启用 HTTPS，限制 CORS 来源，配置请求限流；
6. 通过环境变量注入密钥，不把生产密码写入仓库。

## 16. 已知限制与演进方向

| 编号 | 限制 | 说明 / 后续方向 |
|---|---|---|
| L-01 | 校园认证为模拟 | 仅校验学号格式；正式环境应接入学校统一身份认证（SRS Q-01） |
| L-02 | 不提供支付与物流 | 由范围决定；如扩展需引入支付、对账与退款 |
| L-03 | 内容初筛未接入 | 仅保留审核流程；可接入文本/图片风控作为初筛线索 |
| L-04 | 通知无自动重试 | 失败仅记录 `FAILED`；可增加重试队列与告警 |
| L-05 | 候选参数 | 24 小时超时、7 天评价、10 条上限均为可配置候选值 |
| L-06 | 用户申诉入口 | 后端接口已提供，前端仅管理端有复核入口 |
| L-07 | 单机部署 | 定时任务与文件存储为单实例设计；多实例需分布式调度与对象存储 |
| L-08 | 无限流/验证码 | 生产环境建议在网关层补充 |
| L-09 | 上传文件仅本地 | 未做病毒扫描、图片压缩与 CDN |
| L-10 | 审计仅应用层只读 | 数据库管理员仍可直接改库，需配合权限与备份策略 |

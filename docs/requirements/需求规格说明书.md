# 1. 项目概述

## 1.1 问题与建设背景

校园内存在教材、电子产品、生活用品、体育用品等闲置物品。现有交易多依赖群聊或朋友圈，常见问题包括：信息分散且难以搜索、物品是否仍可交易不明确、沟通与约定缺少结构化记录、多人同时求购可能导致重复成交、交付后缺少评价依据、违规商品与违规用户处置不可追踪。

本项目拟建设面向校园内部用户的二手交易与物品流转平台，将“身份认证—发布审核—搜索发现—收藏咨询—请求确认—线下交付—评价举报—管理处置—统计分析”纳入可追踪的业务闭环。

## 1.2 业务目标与成功指标

| 目标编号 | 业务目标 | 可观察的成功指标 | 状态    |
|---|---|---|-------|
| BG-01 | 提高校园闲置物品供需匹配效率 | 支持关键词、类别、价格、成色和区域组合筛选；候选指标：95% 普通查询 2 秒内返回 | 已确认   |
| BG-02 | 降低无效沟通与重复成交 | 商品状态对用户可见；同一商品同一时刻最多存在 1 个已接受且未终结的订单；待确认请求可多条并存但受上限约束 | 团队已确认 |
| BG-03 | 形成可信的校内交易闭环 | 交易双方均经过校园认证；完成交易具有订单和双方交付确认记录 | 团队已确认 |
| BG-04 | 提升违规治理与追责能力 | 商品、用户、消息可举报；审核、下架、封禁和解封具有理由及审计记录 | 团队已确认 |
| BG-05 | 支持运营改进 | 可按时间、类别和状态查看发布量、成交量、成交率、举报及处置统计 | 团队已确认 |

目标层级关系见 M-01《平台业务目标树》。数值指标是课程分析候选值，不代表真实学校服务承诺。

## 1.4 系统范围

### 1.4.1 范围内

1. 注册、登录、校园身份认证和账户状态管理。
2. 商品草稿、提交审核、批准/驳回、编辑、主动下架和违规下架。
3. 商品浏览、关键词搜索、组合筛选与排序。
4. 收藏、取消收藏和基于商品的咨询会话。
5. 创建待确认请求、卖家接受/拒绝、取消和交易确认。
6. 线下交付时间/区域约定及买卖双方分别确认。
7. 交易评价、商品/用户/消息举报及结果查询。
8. 管理员商品审核、举报处理、账户警告/限权/封禁/解封。
9. 商品、订单和举报状态流转与审计。
10. 发布、交易、评价、举报与处置的聚合统计。

### 1.4.2 非目标

- 不提供在线支付、资金托管、退款结算或发票。
- 不提供校外快递、即时配送或平台自建物流。
- 不对商品真伪、质量和合法来源作线下鉴定。
- 不执行学校纪律处分或司法裁决，只执行平台权限范围内的内容和账户处置。
- 当前不支持拍卖、以物易物、多件购物车和校外公开交易。

“不提供线上支付和物流”是为控制课程项目复杂度提出的范围候选，须由团队或教师确认。

# 2. 用户需求

## 2.1 用户角色

| 角色 | 定义 | 主要目标 |
|---|---|---|
| 游客 | 尚未建立有效登录会话的人 | 注册、登录、查看规则与帮助 |
| 未认证注册用户 | 已注册但未完成校园身份认证 | 完成认证，了解权限限制 |
| 已认证校园用户 | 认证成功且账户可用的校内用户 | 浏览、发布、收藏、咨询、交易、评价和举报 |
| 买家 | 已认证用户在某条待确认请求或订单中的购买角色 | 找到商品、沟通、创建待确认请求和确认交付 |
| 卖家 | 已认证用户在某件商品/订单中的出售角色 | 发布商品、处理订单和确认交付 |
| 管理员 | 具有审核、治理、统计及审计权限的人员 | 审核内容、处理举报、处置账户和查看统计 |

买家和卖家不是互斥账户类型，同一已认证用户可在不同交易中承担不同角色。

## 2.5 代表性详细用例

### UC-02：发布商品并提交审核

| 要素 | 说明 |
|---|---|
| 编号与名称 | UC-02 发布商品并提交审核 |
| 参与者 | 主参与者：卖家；支持参与者：管理员、内容初筛服务（可选） |
| 触发事件 | 卖家选择“发布商品” |
| 前置条件 | 已登录并完成校园认证；账户正常且未被限制发布 |
| 预期频率 | 待用户调研；当前不编造频率 |
| 关联规则 | BR-01～BR-04、BR-16 |

主流程：

1. 卖家创建商品草稿，系统分配商品编号，状态为“草稿”。
2. 卖家填写标题、分类、成色、描述、价格、交付区域和图片。
3. 卖家提交审核，系统校验必填项、格式和账户权限。
4. 校验成功后商品进入“待审核”，系统生成审核任务。
5. 管理员查看商品及初筛标签，依据发布规则作出决定。
6. 管理员批准后商品进入“在售”，系统通知卖家并允许被搜索。

替代及异常流程：

- A1：字段缺失或格式错误，系统定位错误，商品保持“草稿”。
- A2：内容疑似违规，系统不自动判定结论，保留“待审核”供管理员检查。
- A3：管理员驳回时必须填写具体原因，商品进入“审核驳回”；卖家可修改后再次提交。
- A4：账户在提交前被限权，系统拒绝提交，状态和审核任务不变化。

成功结果：商品经审核进入“在售”，审核人与时间可追踪。  
失败结果：不产生公开商品；草稿或驳回记录保留。  
验收标准：对应 AC-01、SC-01、PV-02；状态转换 ST-I01～ST-I05。

### UC-04：搜索与筛选商品

| 要素 | 说明 |
|---|---|
| 编号与名称 | UC-04 搜索与筛选商品 |
| 参与者 | 已认证校园用户（主要为买家） |
| 触发事件 | 用户进入市场页或提交搜索条件 |
| 前置条件 | 用户已登录并完成校园认证 |
| 预期频率 | 高频用例；具体日均次数待运营数据验证 |
| 关联规则 | BR-01、BR-14、BR-15 |

主流程：

1. 系统默认展示“在售”商品。
2. 用户输入关键词，可同时选择类别、价格范围、成色和校内交付区域。
3. 用户选择按发布时间或价格排序。
4. 系统返回同时满足全部条件的在售商品及结果数量。
5. 用户打开详情，查看商品、卖家必要信誉和风险提示。

替代及异常流程：

- A1：关键词为空，系统返回默认在售列表，而不是报错。
- A2：无匹配项，系统显示空结果和清除条件入口。
- A3：商品在查询后被锁定/下架，进入详情时显示最新状态并禁用创建待确认请求/接受。
- A4：输入含特殊字符，系统安全处理，不产生注入或页面脚本执行。

成功结果：结果满足全部条件且状态最新。  
失败结果：明确显示无结果或服务异常，不返回不符合条件的商品。  
验收标准：AC-03、SC-02、PV-01；NFR-01、NFR-04。

### UC-07/UC-08：创建待确认请求并由卖家接受

| 要素 | 说明 |
|---|---|
| 编号与名称 | UC-07 创建待确认请求；UC-08 接受或拒绝待确认请求 |
| 参与者 | 买家、卖家；系统负责并发校验 |
| 触发事件 | 买家点击“创建待确认请求”；卖家随后接受或拒绝 |
| 前置条件 | 双方已认证且账户可交易；商品在售；买家不是卖家；该买家对该商品无待确认请求；该商品待确认请求未超过上限 |
| 预期频率 | 核心高频交易用例；具体频率待统计 |
| 关联规则 | BR-01、BR-05～BR-08、BR-19 |

主流程：

1. 买家查看商品状态与线下交易风险提示。
2. 系统再次校验商品在售、买家非卖家、账户可交易、该买家对该商品无待确认请求、该商品待确认请求未超过上限。
3. 系统生成“待确认请求”（状态记为“待卖家确认”，不锁定商品）和唯一请求号。
4. 卖家查看待确认请求并选择接受。
5. 系统原子校验商品仍为“在售”且不存在其他已接受且未终结的订单。
6. 被接受请求进入“待线下交付”，商品同步进入“已锁定”，同一商品其他待确认请求自动进入“已取消（未中选）”并通知对应买家，系统通知双方。

替代及异常流程：

- A1：卖家拒绝，待确认请求进入“已取消”，商品保持在售。
- A2：买家在卖家接受前取消，待确认请求取消，商品保持在售。
- A3：超过候选时限仍未确认，系统取消待确认请求；时限暂按 24 小时候选，待确认。
- A4：两个待确认请求竞争同一商品；卖家接受一条后，该请求锁定商品，另一条由系统取消（未中选）并通知；对其他请求的接受操作失败并提示“请求已失效/商品已锁定”。
- A5：锁定商品或更新请求/订单任一失败，整个事务回滚，避免跨对象状态漂移。

成功结果：恰好一个被接受请求待交付，商品已锁定；其余请求已取消（未中选）。  
失败结果：不产生两个已接受订单；失败接受与商品状态保持一致。  
验收标准：AC-05a/AC-05b、SC-04、PV-05a/PV-05b；ST-O01～ST-O05、ST-O04a、ST-I06；并发指标 NFR-02。

### UC-10：约定并确认线下交付

| 要素 | 说明 |
|---|---|
| 编号与名称 | UC-10 约定并确认线下交付 |
| 参与者 | 买家、卖家；争议时管理员参与 |
| 触发事件 | 卖家接受待确认请求后，双方约定并实际完成线下交付 |
| 前置条件 | 订单为“待线下交付”，商品为“已锁定” |
| 预期频率 | 每笔被接受订单通常一次；重复修改约定频率待确认 |
| 关联规则 | BR-08～BR-10、BR-16 |

主流程：

1. 双方设置交付时间、校园区域和备注；系统记录修改历史并通知对方。
2. 双方线下验货、付款和交付，平台不代管资金。
3. 买家确认交付，系统记录买家确认时间，订单进入“买家已确认”。
4. 卖家确认交付，系统记录卖家确认时间。
5. 系统在同一一致性边界内将订单置为“已完成”、商品置为“已售”，并开放评价入口。

替代及异常流程：

- A1：卖家先确认，则订单进入“卖家已确认”，等待买家。
- A2：尚无人确认时任一方按规则取消，订单取消；商品在未违规时恢复在售。
- A3：一方已确认后普通取消被拒绝，系统提示提交争议。
- A4：任一方提交争议，订单进入“争议中”，商品保持锁定，管理员处理前不得重新上架。
- A5：完成订单和更新商品任一写入失败，事务回滚到原状态并提示重试。

成功结果：双方确认记录完整，订单完成、商品已售且可评价。  
失败结果：不会因单方确认自动完成，不会把争议商品恢复在售。  
验收标准：AC-06、SC-02/SC-05、PV-03/PV-06；ST-O06～ST-O12、ST-I07～ST-I08。

### UC-13：处理举报并执行账户处置

| 要素 | 说明 |
|---|---|
| 编号与名称 | UC-13 处理举报与账户处置 |
| 参与者 | 管理员；举报人和被举报人接收可公开结果 |
| 触发事件 | 管理员领取一条“已提交”举报 |
| 前置条件 | 管理员已登录且具备相应对象和动作权限；举报对象与证据可访问 |
| 预期频率 | 取决于实际违规量，当前无数据，待确认 |
| 关联规则 | BR-03、BR-12～BR-16、BR-18 |

主流程：

1. 管理员领取举报，系统记录处理人并将状态改为“处理中”。
2. 管理员查看举报说明、对象快照、相关历史和证据。
3. 管理员判断举报成立，填写规则依据、事实理由和处置动作。
4. 系统执行商品违规下架，并按权限对用户执行警告、限权或封禁。
5. 系统保存处置人、时间、前后值、理由和关联举报，通知相关方可公开结果。
6. 处置完成后举报进入“已关闭”。

替代及异常流程：

- A1：证据不足，管理员要求补充，举报进入“待补充”。
- A2：举报不成立，管理员填写理由后结案，不执行惩罚性动作。
- A3：商品存在已接受且未终结订单，商品违规下架，订单转争议/人工处理，不静默取消。
- A4：被处置方按制度提出申诉，举报进入“申诉中”；申诉时限和复核角色待确认。
- A5：管理员缺少权限或未填写理由，系统拒绝处置，举报状态保持。

成功结果：举报、商品、账户、订单和审计记录保持一致。  
失败结果：无权限或缺少依据时不执行处置；原始证据不被覆盖。  
验收标准：AC-09、SC-06、PV-07；ST-R01～ST-R08、ST-I10。

# 3. 领域与数据

## 3.1 统一术语

| 术语 | 统一定义 |
|---|---|
| 校园用户 | 已注册的平台用户；完成校园认证后才具有交易权限。 |
| 买家/卖家 | 用户在具体商品或订单中的业务角色。 |
| 商品 | 一件闲置物品的结构化发布信息，不等同于实际物品所有权证明。 |
| 待确认请求（购买申请） | 订单处于“待卖家确认”状态时的业务称谓；非约束、不锁定商品、可多条并存，受 BR-19 上限约束。 |
| 活跃订单 | 已卖家接受且未终结的订单，即“待线下交付、买家已确认、卖家已确认或争议中”；同一商品最多 1 条。 |
| 未中选 | 卖家接受同一商品的其他请求后，本请求由系统置为“已取消”，取消类型为“未中选”。 |
| 商品锁定 | 商品已有被卖家接受且未终结的订单；待确认请求不构成锁定，可继续创建，但不能再被接受。 |
| 线下交付记录 | 约定时间/区域、双方确认和相关备注；不代表平台提供物流。 |
| 审核 | 管理员对商品是否允许公开展示的决定。 |
| 举报 | 用户针对商品、用户或消息提交的违规线索。 |
| 处置 | 管理员基于依据执行下架、警告、限权、封禁或解封。 |
| 审计日志 | 对关键操作的操作者、时间、对象、理由和前后值的追加式记录。 |

## 3.2 领域模型

核心领域模型见 M-05《领域类图》。主要关系如下：

- 用户 1—N 发布商品；商品 1—N 包含图片。
- 用户与商品通过收藏形成 N—M 关系。
- 商品 1—N 产生咨询会话；会话 1—N 包含消息。
- 商品 1—N 存在历史订单/待确认请求；同一时刻最多 1 个已接受且未终结的订单；待确认请求可多条并存（≤10）。
- 订单各关联 1 名买家和 1 名卖家；订单 1—0..1 当前交付记录，1—0..2 评价。
- 用户、商品和消息可被多次举报；举报可关联多条处置动作。
- 商品、订单、举报和处置的关键变化均进入审计日志。

# 5. 行为与状态

## 5.1 核心业务过程

完整活动图见 M-04《商品发布至交易完成活动图》。主过程为：

1. 卖家创建草稿并提交审核。
2. 管理员批准后商品在售；驳回则卖家修改重提。
3. 买家搜索、收藏、咨询并创建待确认请求。
4. 卖家接受待确认请求，系统原子锁定商品并取消同商品其他请求；或拒绝/超时取消。
5. 双方约定校内线下交付并完成验货、付款和交付。
6. 双方分别确认；均确认后订单完成、商品已售。
7. 双方评价；用户可举报，管理员按证据处置。

## 5.3 订单生命周期

图：M-07《订单状态图》。关键生命周期为：

`待卖家确认（待确认请求）→ 待线下交付 → 买家已确认/卖家已确认 → 已完成`

可从待卖家确认进入“已取消”（买家取消、卖家拒绝、超时、未中选），从待线下交付进入“已取消”（无人确认时）；从交付及单方确认状态进入“争议中”；争议由管理员裁决为“已完成”或“管理关闭”。完整 ST-O01～ST-O12、ST-O04a 条件、业务结果和失败处理见 A 报告 A.4.2。

特别约束：

- 待卖家确认是**待确认请求**，不锁定商品；商品在售期间可继续接收新请求，但受 BR-19 上限约束。
- ST-O02 与 ST-I06 必须原子完成；接受成功后，同一商品其他待确认请求由系统置“已取消（未中选）”（ST-O04a）并通知，不得产生第二个已接受订单。
- ST-O09/O10 与 ST-I08 必须保持一致。
- 一方确认后普通取消是“状态保持”的拒绝，不是成功转换。
- 重复确认请求应幂等，不产生重复评价资格或重复通知。

## 5.4 举报生命周期

图：M-08《举报状态图》。生命周期为：

`已提交 → 处理中 → 已成立/不成立 → 已关闭`

证据不足时可进入“待补充”并返回处理中；成立后按制度可进入“申诉中”。完整 ST-R01～ST-R08 见 A 报告 A.4.3。

## 5.5 异常处理

| 异常 | 检测条件 | 用户提示与处置 | 数据/状态结果 |
|---|---|---|---|
| 未认证或被限权 | 权限校验失败 | 说明认证或限制原因，提供可用入口 | 不创建商品/待确认请求/消息，状态保持 |
| 多个待确认请求竞争 | 商品已被其他请求锁定，或已存在已接受且未终结订单 | 提示“商品已被其他请求锁定”；未中选买家收到取消通知 | 仅 1 条请求→待线下交付，商品锁定 1 次；其余请求→已取消（未中选），不产生第二个活跃订单 |
| 通知失败 | 通知服务返回失败/超时 | 核心操作仍显示成功，通知稍后重试 | 核心状态保留；通知标记失败 |

| 写入中途失败 | 订单与商品更新未全部成功 | 返回明确失败并允许重试 | 整体回滚或通过一致性补偿恢复 |

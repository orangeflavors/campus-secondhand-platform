## 1 这段代码如何执行？

### 输入

- HTTP：`POST /api/orders/{id}/accept`，无请求体；Bearer JWT。
- 业务输入：订单/待确认请求 `id`；当前登录用户 `principal.id()`。
- 配置输入：`app.order.timeout-hours=24`、`app.order.max-pending-per-item=10`（均为 SRS 候选值）。

### 关键条件

1. `SecurityUtils.requireVerified()`：认证状态必须为 `VERIFIED`，否则 403/40301。
2. `SecurityUtils.requireNotBanned()`：账户不得为 `BANNED`，否则 403/40302。
3. 订单必须存在（404），且 `snapshot.sellerId == sellerId`，否则 403/40303。
4. 订单状态必须为 `PENDING_SELLER`（409/40901）。
5. 商品必须存在且为 `ON_SALE`；商品不得已有 `DELIVERING/BUYER_CONFIRMED/SELLER_CONFIRMED/DISPUTE` 活跃订单。
6. 数据库唯一索引 `uk_order_active_item`、`uk_order_pending_buyer` 作为最后兜底。
7. 事务默认传播、默认隔离级别（本项目 MySQL 实测 `REPEATABLE-READ`，应用未显式指定）。

### 调用顺序

```text
OrderController.accept
  → requireVerified / requireNotBanned
  → OrderService.accept (@Transactional)
      1. requireOrder(orderId)                  // 非锁定读
      2. 校验 sellerId、PENDING_SELLER
      3. itemMapper.findByIdForUpdate(itemId)   // 商品行锁
      4. orderMapper.findByIdForUpdate(orderId) // 订单行锁
      5. 复核订单状态、商品 ON_SALE、无活跃订单
      6. orderMapper.update(order)              // PENDING_SELLER → DELIVERING
      7. itemMapper.updateStatus(item)          // ON_SALE → LOCKED
      8. handoverMapper.insert(handover)        // 创建交付记录
      9. orderMapper.findOtherPending(itemId, orderId) // 非锁定读
         → 逐条 update 为 CANCELLED / NOT_SELECTED
         → 逐条 notificationService.send(...)
     10. 通知被接受买家
     11. auditService.log("ORDER_ACCEPT", ...)
     12. detailInternal(...)                    // 返回 OrderVO
```

通知通过 `afterCommit` 在事务提交后以独立事务写入；审计写入在当前事务内，异常被 `AuditService` 吞掉，不回滚业务。

### 会修改的数据

| 表 | 变化 |
|---|---|
| `trade_order` | 被接受订单：`status=DELIVERING`、`accepted_at`、`version+1`；其他可见 PENDING 请求：`status=CANCELLED`、`cancel_type=NOT_SELECTED`、`cancel_reason`、`closed_at`、`version+1` |
| `item` | 被接受订单的商品：`status=LOCKED`、`version+1` |
| `handover_record` | 插入一条交付记录（`order_id`、`updated_by`） |
| `notification` | 提交后插入：“卖家已接受你的请求”“待确认请求未中选” |
| `audit_log` | 插入 `ORDER_ACCEPT`（仅被接受订单；自动未中选没有） |

### 已确认的接口/设计约束

- 接受接口仅允许“已认证 + 未封禁”的订单卖家调用；管理员不得代替普通卖家接受（SRS 权限矩阵，`E-04_角色权限矩阵.csv`）。
- 设计规定接受请求固定“商品行 → 订单行”加锁顺序；接受、商品锁定、其他请求取消在同一事务（`docs/design/系统实现说明.md:111,150`）。
- 通知失败不回滚核心业务，通知在事务提交后写入（BR-17 / `NotificationService.java:55-64`）。
- 数据库层 `active_item_key` 唯一索引只保证“最多 1 条活跃订单”，**不能**保证“其余 PENDING 请求被取消”；后者必须由应用事务完成。

## 3 我的判断是什么？

### 结论总览

| 编号 | 判断 | 严重度 | 依据 |
|---|---|---|---|
| F1 | **已发现问题**：并发窗口下，接受事务会漏掉已提交的新待确认请求，导致商品已锁定但该请求仍为 `PENDING_SELLER` | 高 | FR-018、BR-19、NFR-02、AC-05b |
| F2 | **已发现问题**：自动“未中选”取消没有写入取消动作的审计日志（仅有 `ORDER_CREATE`） | 中 | BR-16、FR-031 |
| F3 | **暂有风险需核验**：接受路径不检查 `expire_at`，过期请求在定时任务扫描前仍可被接受 | 中 | BR-07（候选值） |
| C1 | **当前证据支持符合要求**：权限边界、正常接受、重复接受、10 并发下唯一活跃订单 | — | FR-018、BR-06、BR-19、NFR-02 |

### F1（已发现问题，高）：旧快照导致并发新请求漏取消

**条件**：目标库使用 MySQL 默认 `REPEATABLE-READ`；接受事务在拿到商品行锁之前，先执行了非锁定读 `requireOrder`（`OrderService.java:125`），该语句建立了事务的一致性读视图。随后另一个买家创建请求 B：`create` 先锁定商品行（`OrderService.java:72`），插入并提交 B；接受事务此时才获得商品行锁。之后 `findOtherPending`（`OrderMapper.xml:44-48`）是普通 `SELECT`，仍使用接受事务在 L125 建立的旧读视图。

**代码会**：只读到旧快照中已存在的待确认请求，看不到 B；于是只取消旧快照中的请求，把被接受订单置为 `DELIVERING`、商品置为 `LOCKED`，提交事务。B 保持 `PENDING_SELLER`，但商品已锁定，B 无法再被接受（409），也不会收到“未中选”通知。

**因此**：FR-018/BR-19 要求的“其余请求→已取消（未中选）并通知”没有完成；NFR-02 的“其余请求失败或已取消（未中选）”不满足。`uk_order_active_item` 只保证没有第二条活跃订单，无法发现“遗留 PENDING”这种状态漂移，所以数据库兜底不会报错。

**实测证据**（隔离库，合成数据）：

```text
商品 104：LOCKED
订单 108（A）：DELIVERING
订单 109（B）：PENDING_SELLER（cancel_type 为 NULL）
B 再次接受：HTTP 409 / 40901「商品已被其他请求锁定或不在售，无法接受」
通知：A 有「卖家已接受你的请求」；B 只有卖家侧「收到新的待确认请求」
审计：B 只有 ORDER_CREATE，没有取消/未中选记录
```

测试用触发器让 B 的 `INSERT trade_order` 在持有商品行锁时延迟 4 秒，从而稳定放大该窗口；触发器只改变时序，不改变 `accept` 的任何 SQL/事务语义。结果 JSON：`review/results/accept-inspect-244598.json`。

**修复方向**（本次未改源码）：在拿到商品行锁之后，用**当前读**读取其他 PENDING 请求，例如 `findOtherPending ... FOR UPDATE` / `LOCK IN SHARE MODE`；或避免在锁前做任何一致性读（先锁商品，再锁定读订单）；或把该事务隔离级别显式设为 `READ COMMITTED`。同时应检查 `orderMapper.update(other)` 的受影响行数，不能默认成功。

### F2（已发现问题，中）：自动未中选没有审计

**条件**：接受事务进入 `for (TradeOrder other : findOtherPending(...))`（`OrderService.java:162`），把其他请求改为 `CANCELLED/NOT_SELECTED` 并发送通知，但循环内没有 `auditService.log`。循环结束后，L176 只为被接受订单写一条 `ORDER_ACCEPT`。

**代码会**：其他请求的状态从 `PENDING_SELLER` 变为 `CANCELLED`，却没有操作者、时间、前后值、原因对应的 `audit_log` 行。实测订单 104/105 自动未中选后，审计表只有 `ORDER_CREATE 104`、`ORDER_CREATE 105`，没有取消审计；订单 103 只有 `ORDER_ACCEPT`。

**因此**：BR-16“状态变更必须记录操作者、时间、前后值及原因”未满足；管理员无法从审计日志还原“谁在何时把哪条请求置为未中选”。设计文档的审计覆盖清单（`docs/design/系统实现说明.md:172`）也漏列“未中选”，与 SRS 的 BR-16 存在口径不一致，需要产品或设计确认；按 SRS 的已确认规则，本项应视为缺陷。

**修复方向**：在循环内为每条 `other` 写审计，例如 `ORDER_NOT_SELECTED`（或复用 `ORDER_CANCEL`），记录 `before=PENDING_SELLER`、`after=CANCELLED`、原因“卖家接受其他请求，未中选”、操作者 seller/系统；并在 `AdminService.ACTION_TEXT` 中补文案。

### F3（暂有风险需核验，中）：接受路径不校验过期时间

**条件**：`accept` 在锁定订单后检查了状态、商品状态、活跃订单（`OrderService.java:137-146`），但没有检查 `order.getExpireAt()`。过期取消完全依赖 `OrderTimeoutScheduler` 每 60 秒扫描一次、每次最多 100 条（`OrderMapper.xml:105-110`、`OrderService.java:726-751`）。

**代码会**：当请求已超过 `expire_at`、但定时任务尚未处理（或任务停摆/积压）时，接受仍返回 200，订单进入 `DELIVERING`、商品锁定。

**因此**：如果团队确认 BR-07 的 24 小时为强约束，则接受路径应在锁内拒绝过期请求（或先执行取消），当前实现存在最长约 60 秒的窗口，任务故障时窗口无限扩大。若团队接受“定时任务最终取消”的最终一致性，则应把该窗口写入设计约束并监控任务延迟。实测订单 110 的 `expire_at` 被置为过去 1 分钟，接受仍返回 200 并进入 `DELIVERING`；随后测试用买家取消清理。

### C1（当前证据支持符合要求的部分）

- **权限边界**：非订单卖家 403/40303；未认证 403/40301；封禁 403/40302；管理员 403；订单卖家 200；重复接受 409/40901。对应 `OrderController.java:52-57` 与 `OrderService.java:126-131`。
- **正常路径**：A→`DELIVERING`、商品→`LOCKED`、B/C→`CANCELLED/NOT_SELECTED`、B/C 收到“未中选”通知、A 写入 `ORDER_ACCEPT`。对应 `OrderService.java:148-177`。
- **并发唯一性**：既有 10 并发测试 9/9 通过（恰好 1 条成功、9 条未中选、商品 LOCKED）；`schema.sql` 的 `uk_order_active_item` 生效。
- **回归**：既有 52 项冒烟测试 52/52 通过；正常接受与权限主路径未回归。

### 缺少的信息或需要继续查看的代码

1. **生产隔离级别**：目标部署是否也是 `REPEATABLE-READ`？代码未显式设置；若改为 `READ-COMMITTED`，F1 的触发条件会变化。需要在目标库执行 `SELECT @@transaction_isolation` 并写入部署约束。
2. **“未中选”是否属于 BR-16 必须审计的“状态变更”**：SRS BR-16 是已确认规则，但设计文档审计清单漏列；需要产品/设计确认口径。本报告按 SRS 判定为缺陷。
3. **BR-07 的 24 小时是否最终确认**：SRS 标注为候选值；若确认，F3 应升级为缺陷，并在接受事务内校验 `expire_at`。
4. **买家账户状态是否应在接受时复核**：UC-07/08 前置条件写“双方已认证且账户可交易”，但 `accept` 只校验卖家，不重新读取买家状态。若买家在请求后被封禁/限权，卖家仍可接受，买家无法确认，订单可能卡在 `DELIVERING`。本次未做故障注入，建议单独核验。
5. **`orderMapper.update` 返回值被忽略**：`OrderService.java:151,167` 均未检查受影响行数；在版本冲突或并发取消时可能静默 0 行。需结合 F1 的修复一起处理。
6. **通知失败重试**：BR-17 只要求记录失败并重试；`NotificationWriter.attemptFailed` 记录 `FAILED`，但是否有重试任务未在本次范围核验。

### 输入或操作

1. **正常接受**：卖家创建并上架商品；买家 A/B/C 各创建 1 条待确认请求；卖家接受 A。
2. **权限边界**：新商品 + A 的请求；分别用买家 B、未认证用户、封禁用户、管理员、卖家调用接受。
3. **并发窗口**：创建 A 的请求；在隔离库创建测试触发器，使新 `trade_order` 插入延迟 4 秒；启动 B 的创建请求，1 秒后启动 A 的接受请求；等待两者完成；删除触发器。
4. **过期接受**：创建 A 的请求；SQL 将 `expire_at` 置为过去 1 分钟；立即调用接受。

### 按需求应该得到

- 正常：A=`DELIVERING`；商品=`LOCKED`；B/C=`CANCELLED` 且 `cancelType=NOT_SELECTED`；B/C 收到“未中选”通知；A 有 `ORDER_ACCEPT` 审计；B/C 有状态变更审计。

- 并发窗口：B 必须被取消为 `NOT_SELECTED` 并收到通知；商品只有 1 条活跃订单。
- 过期：接受应失败（409/业务提示），订单保持 `PENDING_SELLER` 或已被定时任务取消；不能进入 `DELIVERING`。
